# Explicit Planned RESOLVE Prefix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Execute and atomically retain an explicit six-stage procurement prefix with pinned candidate input, mention-bound identity evidence and truthful abstentions, preserving every existing five-stage caller.

**Architecture:** Reuse the existing admitted first-five runner and its exact receipt; admit and invoke one separate registered RESOLVE executor. Neutral frozen records validate inputs, row membership, receipts and archive binding; procurement owns the existing matching rule and namespace policy. An additive Postgres capability publishes source/prefix/catalog/resolution together, behind a neutral port and explicit bootstrap wiring.

**Tech Stack:** Python stdlib dataclasses/Protocols/argparse/JSON, existing SemanticCodec, optional psycopg/Postgres16, pytest; no new dependencies or model calls.

**Spec:** [Approved design](../specs/2026-10-24-planned-resolve-prefix-design.md), owner-approved proposal `052ab479116fa35704cb3a5f970f89d19b337bea` on 2026-10-24; [ADR-046](../../adr/046-explicit-planned-resolve-prefix.md), decision #235. Implementation [#236](https://github.com/stauntonjr/procurement-intelligence-lab/issues/236), primary M3, native parent #14. Baseline main `88d32d4f5da0f5cae500d465f80173b213ee71d0`.

**Plan status:** Prepared for owner review; product implementation has not started. Preserve the established Native/inline method and one independent final architecture/semantic review. Design approval does not establish runtime acceptance or plan review.

## Global Constraints

- Core owns semantics; adapters own mechanics. Use stdlib frozen dataclasses and Protocols; neutral platform/ports import no procurement, DB or framework. Bootstrap is the visible composition root.
- Actual stages are INGEST-through-RESOLVE. All six later declarations remain NOT_EXECUTED, including unvisited EMPTY bindings. Prefix completion is distinct from package completion and resolved identity.
- Support only `procurement_item` / `internal_sku` under an explicit procurement policy. Candidate keys are raw internal-SKU canonical keys; no aliases, automatic entity creation or source-derived candidate catalog.
- Candidate JSON: **32KiB, 256 keys, 256 Unicode characters per key**; exact duplicate raw keys reject, normalized collisions remain ambiguous. Empty catalog is valid evidence; missing catalog is an input error. Preserve raw key text; do not silently trim/casefold the returned canonical key.
- Exact four-part scope including version; source observation and candidate effective time <= pinned capture/start as-of. Preserve encoded fixed offsets in identity. No implicit latest snapshot or invented staleness limit.
- Reuse the unchanged `normalize_identifier`/`resolve_identifier` matching rule. Bind evidence from the actual mention row rather than legacy subject-text lookup. No score, threshold, probability, model/provider swap or general ER-quality claim.
- Keep all original source claims and one audited outcome per mention. Only resolved rows get canonical links. Null/blank-SKU rows remain unlinked claims; empty output requires a real batch/event.
- Separate six-stage request/invocation/output/receipt/archive types. Do not widen `PREFIX`, ExecutionRequest, StageInvocation, PrefixExecutionReceipt, DocumentSnapshot, local_prefix_jobs/v1 or their codec/wire semantics.
- One transaction publishes captured source, the unchanged five-stage snapshot/prefix binding, candidate raw/canonical input and the six-stage result. First-retained receipts stay distinct from current invocation receipts. Ambiguous commit acknowledgement never proves rollback.
- Reuse **16MiB / 50,000-node / depth64** allowlist-codec bounds. Original metadata files keep existing **1MiB/32KiB** bounds. History defaults100/max200, nonnegative after_sequence, limit+1 evidence; no inferred total. Export is atomic and refuses overwrite.
- Persist no DSN/secret/callback/exception trace or environment credential. Optional storage remains optional for base execution. Use only synthetic data; all input paths and candidate catalogs are explicit.
- No later-stage or governing authority, global identity, substitutions, fuzzy matching, six-stage durable jobs, queue/listener/worker/lease, automatic recomputation, operational-agent tool/permission, deployment or model spend. Broad #14/#42/#39/#43/#45/#36 remain open.

## Review Focus

1. A reformatted/reordered catalog must preserve semantic computation identity while retaining different raw JSON/checksum audit evidence; Tasks1/3/4/6 test current versus first-retained receipts.
2. The five-stage computation may already be archived with an earlier completion receipt; the new six-stage result must retain its actual embedded prefix and separately bind the first archived prefix, without falsely requiring receipt equality; Tasks4/5/6 cover this through Postgres and public recovery.
3. Identical mention text in duplicate source rows must never share or substitute row evidence or hide unlinked null-SKU claims; Tasks1/2/3/6 assert one-to-one mention coverage and exhaustive linked/unlinked membership.
4. Unsupported sixth metadata or namespace must fail before an intentionally absent source or DB connection; equal instants with different offsets retain their exact identity encoding; Tasks1/2/3/6 test the actual admission/public boundary.
5. Recomputed outer checksums must not bless a swapped catalog, raw JSON, policy, row, receipt or source membership; Tasks1/4/5/6 test intrinsic and domain validation on source-free recovery.

| Record | Fields / derived behavior |
|---|---|
| CandidateSnapshot | schema_version exactly1.0, catalog_id, catalog_revision, scope, entity_type, identifier_namespace, effective_at, keys; keys are an immutable canonically ordered raw-key tuple; snapshot_id/content_digest cover every field |

| ResolutionPolicyEvidence | reference:ResolvedReference, entity_type, identifier_namespace, parameters:tuple[tuple[str,str],...]; sorted unique immutable parameter names; reference.content_digest equals digest(dict(parameters)), with matching entity_type/identifier_namespace parameters |
| MentionResolution | mention:EntityMention, decision:ResolutionDecision, candidate_snapshot_id, matched_keys:tuple[str,...], policy_reference; outcome_id binds mention ID, full decision and audit metadata |
| ResolvedOutput | previous:AssertedOutput, candidates:CandidateSnapshot, policy:ResolutionPolicyEvidence, outcomes:tuple[MentionResolution,...], canonicalized:tuple[CanonicalizedAssertion,...], unlinked_assertion_ids:tuple[str,...], provenance:DecisionProvenance; source/event/batch_id/input_ids/reference_ids are derived |
| ResolvedExecutionRequest | prefix:ExecutionRequest, candidate_input:CandidateInputEvidence, policy:ResolutionPolicyEvidence, stop_after:StageId; requires RESOLVE, exact scope and time admission |
| ResolveInvocation | provenance, captured_at, references:tuple[ResolvedReference,...], candidate_snapshot_id; stage is always RESOLVE; deterministic component metadata only |
| ResolvedPrefixExecutionReceipt | prefix:PrefixExecutionReceipt, candidate_input, policy, output:ResolvedOutput, entries:tuple[StageExecutionEntry,...], completed_at; plan/context derive from prefix; separate computation_payload/execution_digest and receipt_digest |

`load_candidate_input(data:bytes)->CandidateInputEvidence` lives in resolution_inputs.py: a pure stdlib JSON system boundary, not source/file access. Exact wire keys mirror CandidateSnapshot fields; `scope` has the existing four string keys, effective_at is aware ISO8601 and keys is a JSON string array. The loader sorts the raw keys; the typed snapshot requires a sorted unique tuple. Use independent key validation rather than the identity-text helper's trimming restriction; raw candidate keys are preserved. Domain validation rejects keys whose normalized form is empty.

`ResolvedOutput` validates exact previous-output membership, original mention order, one outcome per mention, no duplicate/cross-row decision/canonical links, complete candidate membership and exhaustive disjoint linked/unlinked source claims. Matched keys use canonical catalog order; canonical links and unlinked IDs follow original source-claim order. Resolved decisions require exactly one matched key equal to canonical_key; abstentions carry no canonical key. Every decision retains the exact sixth provenance. The domain validator additionally checks the actual matching rule, supported namespace/type, HAS_SKU predicate/raw value and rationale. Canonical effective time is the pinned resolution as-of; original source effective times stay unchanged.

The computation payload is an explicit projection of the embedded **five-stage computation payload**, candidate semantic snapshot, policy, sixth output and twelve entries. It must not accidentally include the embedded completion time, candidate raw bytes/checksum or final completion time. Receipt identity retains all those audit fields. Event/batch identities use input/output IDs and provenance, never their own event/receipt IDs.
